# Automatic thinking cycle

Main chat enables the cycle at launch. After 30 seconds idle, Marionette gets an internal step with the most recently active conversation, current soul, contact notes, and all three scratchpads. Before any user turn, that scope is the selected terminal contact. A successful ordinary input updates the active scope and restarts the idle delay. Histories remain separate; the cycle does not merge other conversations into this one.

The model can review context, choose a useful step, call any registered tool, evaluate the result and update its working state. Available tools are `read_scratchpads`, `update_scratchpad`, `update_soul`, `update_contact_notes` and `query_logs`. It need not call every tool. Notes remain bound to the active contact; log queries remain bound to that conversation/session. The trigger supplies the latest real input ID when available. Message diagnostics use that known ID; `previous_message` is unavailable for internal triggers. Setup/current status remain available. Docs-vault access stays disconnected.

The final result is a JSON object with `action` (`continue` or `wait`) and a `summary` of at most 1,000 characters. Continue schedules another step after 30 idle seconds; wait suspends until an ordinary message or operator resume. Invalid results, limits and errors also wait. The app does not interpret free-form Intentions as executable schedules. Existing feature guidance and the editable soul remain supplied; `prompts/thinking-cycle.md` adds cycle-specific instructions.

## Controls and limits

Owner terminal commands are `/thinking on`, `/thinking off`, and `/thinking status` (bare `/thinking` also reports status). These control the cycle, not the model's reasoning mode. Discord messages do not control these commands. Launch defaults to on; restart discards the scheduler state. `/clear` and `/resetmemory` suspend cycles until new input or resume. Reset clears the pads as before.

Each step has up to four model requests, eight tool calls, 2,048 generated tokens per model request, and a cooperative 30-second deadline. This shorter internal output cap deliberately favors responsiveness over the publisher's usual 32,768-token allowance; complex reasoning can hit the cap and wait. Ordinary user output limits, sampling, model and native template remain unchanged. The bound is up to 8,192 generated tokens per step, including reasoning and tool requests, not an unlimited background generation.

The existing terminal loop drives scheduling; there is no new process, inference slot or worker. Input has priority before starting a step. During a step, pending Discord input and submitted terminal input are checked on streamed chunks and before each tool dispatch. A detected input closes the stream and yields; completed writes remain saved. This is cooperative cancellation: model prompt processing, token-counting HTTP calls and an already executing tool cannot be interrupted immediately. Input typed without Enter is not yet a submitted terminal message. Pending cache preparation completes first. User turns themselves retain existing behavior.

## Results, context and storage

Internal reasoning and the cycle summary appear in the local terminal and existing logs. They are not sent as Discord replies. The cycle cannot spontaneously send a message with the current tool set. A later user reply can refer to the retained internal exchange in that conversation.

Application triggers are stored as `system/cycle_trigger`, and final results as `assistant/cycle_result`. They are not fabricated user input records and do not displace real-input anchors used by log queries. Native in-memory history uses a labeled user-role trigger so complete-cycle exchanges trim together with tool calls/results. Interrupted exchanges are not retained in history, although already completed tool edits survive. Logs retain ordinary diagnostic evidence under the existing RAM policy. Routine conversation/terminal records are still durable and uncapped; running many cycles increases those records. No new per-event diagnostic disk writer is introduced.

Focus, Working Space and Intentions remain shared RAM state across conversations. Contact notes and soul edits remain persistent. There is no unified cross-contact history, unattended external messaging, long-term scratchpad store, or claim of consciousness. Useful autonomous behavior depends on the model; scheduling and tool access alone do not establish it.

## Verification — 2026-11-12

The full regression run passed 169 core and 14 mocked Discord tests. After adding explicit model/tool-call cap coverage and tightening reset scope, all five focused thinking tests and six reset tests passed. Coverage includes every production tool bound during an internal turn, native Qwen-Agent dispatch over mocked HTTP, no fake user-input database rows, wait/continue scheduling, stream cancellation before an edit, preserved history on interruption, call caps, and restoring ordinary API state afterward.

Two isolated real 4B runs triggered automatically after idle without an ordinary user request and exited cleanly. The first read scratchpads, unnecessarily copied supplied identity metadata into contact notes, and chose wait. Guidance was tightened to discourage metadata duplication. The second read scratchpads and edited Focus, but chose continue while its summary said it was awaiting input; it also said “systems nominal” without a status lookup. This verifies automatic scheduling and real tool use, not reliable relevance, truthful status summaries, or appropriate stopping decisions. The continuation decision is taken from the JSON action; prose is not a verified status report. Long-running cycles and real Discord interruption have not been live-tested. Production chat and Discord stayed off; synthetic profiles and temporary logs were used.
